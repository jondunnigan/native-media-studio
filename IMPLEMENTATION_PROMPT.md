# Implementation Prompt: Native Media Studio

Copy the following prompt into a coding agent when you need it to build or recreate this project. It is intentionally explicit about the product contract, non-goals, data lifecycle, and acceptance criteria.

```text
Build a production-minded, self-hostable web application called “Native Media Studio.” It is a private conversion workspace for users to retrieve YouTube media only when they own the content or are otherwise authorized to download it. Do not implement DRM bypassing, login circumvention, cookie-import workflows, paywall bypassing, CAPTCHA bypassing, or support for arbitrary video hosts. The app may inspect only youtube.com, m.youtube.com, and youtu.be URLs.

Use this technology stack unless an existing repository already dictates an equivalent stack: React 19 + TypeScript + Tailwind CSS for the frontend; Node.js + Express + TypeScript for the backend; MySQL-compatible database with Drizzle ORM for job metadata; yt-dlp as the only media retrieval and inspection executable; ffmpeg as the only stream merger and audio converter. Use Server-Sent Events (SSE), not polling alone and not a WebSocket dependency, for live conversion status. The complete self-hosted deployment must use Docker Compose and expose exactly one public HTTP port.

The user-facing interface must be refined and Apple.com-inspired without copying Apple assets or trademarks. Use a pure white/off-white background, Inter or SF Pro system fallback typography, very large bold hero text, generous whitespace, quiet blue/purple gradient accents, subtle frosted-glass cards, hairline borders, restrained shadows, high quality iconography, excellent responsive behavior, keyboard-visible focus states, and short spring-style transitions. Avoid a generic admin dashboard. The app should feel like a focused premium consumer utility.

Build the following flow exactly.

1. Landing and source input: Display a minimal top navigation, a hero that explains that the app is private/self-hosted and temporary, and a prominent YouTube URL input. Require an unchecked acknowledgement reading substantially “I own this content or have permission to download it” before source inspection and conversion can be submitted. Do not pre-check it. Validate URLs on both client and server; only accept http/https canonical YouTube hosts listed above.

2. Metadata inspection: On submit, run yt-dlp on the server with --no-playlist, --skip-download, and --dump-single-json. Do not download media during inspection. Return and render title, thumbnail, duration, source ID, and a normalized subset of available formats. Treat parse errors, unavailable videos, private videos, region restrictions, and malformed sources as clear user-facing errors. Do not pretend that a source can be retrieved when it cannot.

3. Video conversion: Provide a Video mode with quality choices Best available, 1080p, 720p, 480p, and 360p, and container choices MP4, MKV, and WebM. The selection behavior must be explicit: Best available selects the best source video plus best source audio. A resolution setting selects the best source video stream at or below that height plus best source audio, with a reasonable yt-dlp fallback for compatible muxed formats. Use yt-dlp to retrieve source streams and invoke ffmpeg through yt-dlp’s merge path. Do not artificially upscale. Explain in the UI that the highest compatible source quality is preserved when available.

4. Audio conversion: Provide an Audio mode with output formats MP3, AAC, FLAC, WAV, and OGG and quality choices Best available, 320 kbps, 192 kbps, and 128 kbps. Use yt-dlp’s audio extraction flags with ffmpeg. The UI must clearly label that a requested output format may require re-encoding; do not claim a lossless “native” copy if an encode is requested.

5. Conversion jobs and data model: Persist a media_jobs table. At minimum store a random nonsequential job ID, anonymous owner session ID, source URL, source ID, title, thumbnail URL, duration, media kind, requested quality, output format, status, integer progress, stage text, output file name, output path, MIME type, file size, SHA-256 hash of the download token, expiry timestamp, downloaded timestamp, failure message, creation time, and update time. Use an enum or controlled set of job states: queued, fetching, downloading, processing, ready, failed, expired, downloaded. Store no media bytes in the database.

6. Progress: Run yt-dlp using child_process.spawn with an argument array, never a shell command string. Enable newline progress output and parse percent updates. Publish job state, stage, and integer progress via an SSE endpoint scoped to the same anonymous owner session. Show a smooth progress bar and status text. The UI must show fetching/preparing, downloading, finalizing/verifying, ready, and failure states. Add a modest polling/refetch fallback for session history but do not use polling as the primary live progress mechanism.

7. Temporary storage and secure downloads: Store temporary media files only in a configurable job work directory such as /app/data/media-jobs/<job-id>. Do not expose the directory as static files. When conversion completes, generate a cryptographically random 256-bit download token, store only SHA-256(token) in the database, and return a link formatted /api/media/download/<job-id>?token=<token>. Enforce that the token hash, ready job state, file existence, and expiry timestamp all match. Set the expiry to exactly 15 minutes after the file becomes ready; never extend that expiry because a link is requested. Send Content-Type and a Content-Disposition attachment header. After a successful completed download, mark the job downloaded, invalidate the token, and delete the entire job directory. Reject expired or invalid tokens with a generic 404-style response.

8. Cleanup with no manual intervention: A completed job must be deleted at expiry even if nobody opens the UI. Do not depend on Node setInterval, node-cron, or an in-process timer. In Docker Compose, add a small independent cleanup service that mounts the same job-files volume and scans ready job folders at least once a minute. The application must write a .ready marker only after recording the file’s expiry. The cleanup service should delete only completed job folders whose .ready marker is more than 15 minutes old. On app startup, perform a best-effort database cleanup of expired ready jobs too. Files that fail conversion must be deleted immediately.

9. Session history: Generate a random anonymous session ID, place it in an HttpOnly SameSite=Lax cookie, and associate it with jobs. In a “Recent files” panel, show only the current browser session’s most recent jobs. Display title, media kind, output format, selected quality, status, size when ready, remaining expiry time, and a download button when ready. State that files are removed after download or after 15 minutes. Never include invented reviews, testimonials, or fake social proof.

10. Docker deployment: Create a root Dockerfile based on node:22-slim. Install ffmpeg, python3, pip, ca-certificates, and yt-dlp. Use corepack with the pnpm version pinned by package.json. Copy repository files, install all dependencies needed for the build, run the full production build, set NODE_ENV=production, and use process.env.PORT. The app must run database migrations before Node starts. Create docker-compose.yml with an app service, a MySQL 8.4 database service, and an independent media-cleanup service. Expose only ${APP_PORT:-3000}:3000 from the app. Use named volumes for MySQL data and media job files. Add .env.example with APP_PORT, MYSQL_PASSWORD, and MYSQL_ROOT_PASSWORD placeholders. A fresh clone must start with: docker compose up --build -d.

11. Documentation: Write a README with one-command startup, a warning to replace default database passwords before public exposure, product behavior table, architecture explanation, all supported output choices, constraints about source availability, responsible-use statement, local development commands, volume cleanup instructions, and security hardening guidance. Make clear that “best” means best available compatible source quality rather than a guarantee that every source or original container is available.

12. Testing and validation: Write Vitest tests for accepted/rejected YouTube URL validation and yt-dlp percentage parsing. Add tests or small pure helpers that prove token expiry checks do not allow an expired job. Run TypeScript checks, tests, and a production build. Verify desktop and mobile UI rendering. If browser/system media binaries are not present in the development environment, do not fake a conversion: document that Docker supplies them and validate the command construction with unit tests.

Required UI copy includes an authorization reminder, “15-minute” temporary file language, and a statement that the application is self-hosted/private. Use no fabricated testimonials, ratings, customer reviews, download counts, or claims of affiliation with YouTube or Apple.

Acceptance criteria: (a) only permitted YouTube hosts reach yt-dlp; (b) a user sees accurate source metadata before creating a job; (c) video and audio output controls behave exactly as specified; (d) live server events update a visible progress bar; (e) download capability uses a random token whose stored database representation is hashed; (f) all completed output files expire after 15 minutes and are deleted on download or expiry; (g) recent jobs are isolated to the same anonymous session; (h) docker compose up --build -d brings up the application, database, and cleanup service while exposing only the web port; (i) Docker image includes Node, yt-dlp, and ffmpeg; (j) TypeScript, tests, and production build pass.
```
